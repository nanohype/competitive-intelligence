# Spike: Claude Tag + MCP port

**Question:** keep the EKS/Platform-tenant shape, drop `@slack/bolt`, and expose
the app as a remote MCP server that Claude Tag (and every other Claude surface)
consumes. Does it make sense, and what do we lose?

**Verdict:** yes, and favorably — but only because the app cleanly splits into a
*push* half and a *pull* half that port differently. The Bolt weight is almost
entirely on the pull half, which is exactly the half that becomes MCP tools. Two
real costs to decide consciously (on-account data boundary; zero-ingress →
authenticated ingress). Nothing about the radar's core changes.

## The split that makes this work

| Half | What it is | Human in loop? | Port |
|------|------------|----------------|------|
| **Push (radar)** | scheduler → `crawlAll` → `ingestAndDiff` (chunk/embed/semantic-diff) → `alertEngine.processDiffs` → alert sink | No — autonomous, scheduled, threshold-gated | **Stays.** Claude Tag is tag-to-act (pull); it does not watch your server and post on change. Keep the alert path. |
| **Pull (query)** | `intel.query(q, {competitor, topK})` → embed → vector search → LLM answer, fronted by `/query`, @mention, DM | Yes — request/response | **Becomes MCP tools.** This is where Bolt dies. |

The seam already exists: alerts dispatch through an `AlertSink` interface, and
`intel.query()` is a pure function of (question) → text. Neither is entangled
with Bolt beyond the thin `src/slack/` layer.

## What the port does

**Delete** (`src/slack/` + `@slack/bolt`):
- `commands.ts` (`/competitive-intelligence query|crawl|status`)
- `handlers.ts` (@mention + DM query, incl. the crude regex competitor extraction)
- the Bolt `App` in `slack/index.ts` — socket mode, HTTP receiver, signing
  secret, port-`+1` juggling, the DM/channel event gating that exists only to
  cap Bedrock spend on stray channel messages

**Add** — a remote MCP server (agent + tools) on the platform:
- `search_intel(question, competitor?, topK?)` → retrieved chunks (the pure
  retrieval; see the on-account note below for whether it also *answers*)
- `trigger_crawl()` → goes through the existing single-writer crawl mutex
- `status()` → uptime/mem/version
- `list_sources()` → the Zod-validated `sources.json` set

**Keep** — a *minimal outbound* alert sink:
- Drop Bolt for the sink; outbound `chat.postMessage` needs only `@slack/web-api`
  + a bot token (the digest-pipeline pattern), not the whole Bolt app.
- Keep `alerts/formatter.ts` Block Kit — deterministic, scannable alerts are the
  radar's product; we do not want threshold-gated alerts re-generated by a model.

**Deployment refinement:** split the one Deployment into two —
- `worker` (scheduler + crawl loop, `replicaCount: 1`, single-writer, **zero
  ingress**, keeps the outbound web-api sink)
- `mcp` (stateless, the inbound connector surface Anthropic's cloud reaches;
  `trigger_crawl` proxies to the worker's mutexed crawl)

This mirrors incident-response's webhook/processor split and keeps the crawler at
zero ingress — only the `mcp` Deployment is exposed.

## What Claude Tag makes strictly better

- The @mention path today does regex competitor extraction and a fixed
  Sonnet-over-top-K answer. Claude Tag's Opus 4.8 *is* the interface: real
  entity extraction, multi-turn refinement, follow-ups, and cross-connector
  reasoning (combine our intel with GitHub/GDrive connectors) — none of which we
  build or maintain.
- Spend + permission control moves from our hand-rolled DM/channel gate to Claude
  Tag's admin spend cap, per-channel scoping, and audit logs — centrally
  administered, better than what we ship.
- Reach: the same MCP server is consumable by claude.ai, Desktop, Cowork, Claude
  Code, mobile — not just Slack. One server, every surface.
- Less code: if answering moves to Claude Tag, `intel/analysis.ts` `answerQuery`
  + the query system prompt + the query-side Bedrock call all go away.

*These are the payoff of the port and, under the resolution below (lean into
Claude Tag), they apply to the query path. A regulated tenant that toggles
`search_intel` to in-boundary-only trades them back for that one tool — a config
choice, not a rebuild.*

## What we lose (decide consciously)

1. **On-account inference — RESOLVED: lean into Claude Tag.** The privacy delta
   is thin and not worth architecting around. The content is already LLM-analyzed
   on-account today, so the real variable isn't *model or not* — it's *which
   processor under what terms*: Bedrock-on-account (your AWS, no training) vs.
   Anthropic Enterprise (no training, zero-retention), the **same trust class**.
   Accept Anthropic as a processor; `search_intel` is a normal MCP tool Claude Tag
   calls. This is what pays for the port (Bolt dies, every-surface reach, managed
   spend + audit, the query LLM path can go).
   - **Ingress — via the tunnel, no inbound port.** Claude reaching the tools does
     NOT open an inbound surface: `eks-gitops` `networking/mcp-tunnel` wraps
     Anthropic's official tunnel — `cloudflared` **outbound-only, no inbound
     ports, no public exposure**, WIF-authed (OIDC → `org:manage_tunnels`,
     short-lived token, chart-managed cert), routing proxy validates upstream IPs
     + routes by hostname to the in-cluster MCP svc. Same zero-inbound shape as
     socket mode. See § Ingress below.
   - **Privacy is a free knob.** Sensitivity = which tools a connector advertises
     = per-tenant config, not a code fork. A regulated tenant exposes
     `search_intel` to in-boundary consumers only and keeps Claude Tag on the safe
     verbs — same server, a deployment toggle. Leaning in forecloses nothing.
   - Radar/alerts unchanged: on-account + direct Slack, no Claude Tag.

2. **Zero-ingress posture — preserved (corrected).** Earlier framing said a
   remote MCP server inverts socket mode's no-inbound-port posture. It does not:
   the mcp-tunnel is outbound-only (`cloudflared`), so the pod keeps zero inbound
   ports and zero public exposure — same shape as socket mode. The work is wiring,
   not a new attack surface (see § Ingress). The one real gate is external:
   Anthropic MCP tunnels are a **research preview — request tunnel access first**.

3. **Deterministic interactive formatting.** Alert Block Kit is kept. But
   interactive *replies* become Claude Tag's prose rather than our formatting —
   fine for conversational Q&A, a change from the current fixed output.

4. **Direct requester identity at the tool boundary.** Today we log
   `command.user_id` / `event.user`. At the MCP boundary the caller is Claude
   Tag's per-channel identity unless it forwards the human. Minor here (the app is
   read-only intel); matters more for incident-response.

## Generalizes to the other three

The push/pull split is the reusable lens. The long-winded Bolt is always the pull
half; that half is always the clean MCP win.

- **slack-knowledge-bot** — nearly all pull (RAG Q&A in Slack). Claude Tag
  overlaps its whole purpose. Port ≈ retirement: keep only the fail-secure
  per-doc ACL re-verify as an MCP tool; the rest is Claude Tag native. *What we
  lose: the app's reason to exist* — that's the point.
- **incident-response** — sharpest split. War-room assembly + Statuspage 2-phase
  approval gate + EventBridge nudges stay as MCP tools + webhook ingress; Claude
  Tag is the trigger + status surface. The **interactive approval buttons**
  (Block Kit actions carrying the 2-phase commit) are the hard residual —
  Claude-Tag-native confirmation vs. a thin retained Slack action surface. Most
  Bolt survives here.
- **digest-pipeline** — no interactive surface; already posts via `@slack/web-api`
  only. Nothing to port. A `query_digest` MCP tool is a bonus, not a port.

## Ingress (how Claude reaches the tools — flexible + secure)

Two tiers by *who reaches in*; they share the tenant `mcp` svc.

**Tier 1 — Claude surfaces (today): the mcp-tunnel addon.** `eks-gitops`
`networking/mcp-tunnel` wraps Anthropic's official tunnel:
- `cloudflared` **outbound-only** — no inbound ports, no public LB, no WAF, no
  IP allow-listing. Zero-inbound posture preserved.
- **WIF auth** — cluster OIDC federates (`org:manage_tunnels`); the chart mints a
  short-lived tunnel token + manages the cert. No static secrets.
- Routing proxy terminates inner TLS, validates upstream IPs, routes by hostname
  → the in-cluster `mcp` svc. `gateway.config.routes` is one entry per exposed
  server — and the tool/tenant exposure control (the privacy knob).
- **NetworkPolicy**: the `mcp` svc accepts ingress ONLY from the tunnel; nothing
  else reaches it.
- Reachable at `https://<subdomain>.<tunnel-domain>/<path>` → hand that to the
  Claude Tag custom connector.
- Gate: Anthropic research preview — **request tunnel access first**.

**Tier 2 — arbitrary / non-Anthropic consumers (only when one appears):** the AWS
ingress stack already in-catalog — `aws-load-balancer-controller` + `external-dns`
+ `cert-manager`, an ALB fronted by AWS WAF (edge in landing-zone), plus an
OAuth/gateway auth layer. This is the real public surface; don't build it
speculatively (incident-response's `webhook-ingress` is the precedent for
authenticated public ingress when it's actually warranted).

**Flexible = productize tier 1 per-tenant.** Today the tunnel is opt-in with
routes hand-filled in `values.yaml`. Reusable version: a declarative field on the
Platform CR / AgentFleet ("expose MCP: [tools]") the `eks-agent-platform` operator
reconciles into (a) the tunnel `routes` entry, (b) the NetworkPolicy tunnel→`mcp`,
(c) the tool-scope. Onboarding a tenant to Claude becomes a config field, not
bespoke ingress work. Boundary-correct: tunnel addon in eks-gitops, per-tenant
wiring in the operator, edge/DNS/WAF in landing-zone only for tier 2.

## Recommendation

Port competitive-intelligence as the pattern-setter: it exercises the full
push/pull split, the two-Deployment refinement, and the tier-1 ingress path,
without incident-response's approval-button hard case. Sequence:

1. Extract `intel.query` + `runCrawl` + `status` + `list_sources` behind an MCP
   server module (all tools on the connector — lean-in resolution).
2. Reduce the Slack sink to `@slack/web-api`; delete `@slack/bolt` + `src/slack/`.
3. Split worker/`mcp` Deployments; enable the mcp-tunnel addon, add the tenant's
   `routes` entry + NetworkPolicy (tunnel→`mcp` only). WIF handles auth — no
   static token, no public ingress.
4. Register the custom connector in Claude Tag; verify @Claude-in-channel →
   `search_intel` end to end.

Prereq: request Anthropic MCP-tunnel access (research preview) — the one external
gate; it blocks step 3.

Decision RESOLVED — lean into Claude Tag (What we lose §1): Anthropic accepted as
a processor; all tools register on the connector. Privacy stays a per-tenant
toggle (expose `search_intel` to in-boundary consumers only) — config, not a fork.
